# Airport 离线地图、旧版 A* 与当前纯 Nav2 多 Go2 围捕实施记录

更新日期：2026-07-21

本文档是 airport 静态围捕方案的主文档。它同时保留地图生成和旧版自研 A* 的设计记录，
并说明当前最终采用的“纯 Nav2 规划与控制”实现。

重要结论：

1. `world_to_grid` 及其 `airport.pgm/airport.yaml` 继续使用；
2. 老师已明确不要求自研 A*，所以 `grid_astar.py + waypoint_encircle.py` 只作为历史实现和
   对照测试，不再进入 airport 当前运行链路；
3. 当前运行入口是新包 `multi_go2_nav2`；
4. 每只狗由一套独立 Nav2 负责规划、连续路径跟踪和速度平滑；
5. 自定义节点只负责围捕点生成、三狗目标分配和可视化，不实现路径规划器或底层控制器；
6. 三只狗共享一张 `/map`，在 RViz 中同时显示规划路径和真实路径。

二、Airport world 离线栅格地图
=============================

2.1 采用离线 world 转换的原因

airport 是完全已知的仿真场景。直接从 world 生成地图可以避免雷达噪声、遮挡、漏扫和建图
耗时；相同输入还会产生字节一致的结果，便于实验复现。地图坐标直接采用 Gazebo world 坐标，
可以与 ground-truth odometry 对齐。

2.2 固定地图参数

  world 范围：x=[-180,180] m，y=[-75,75] m
  分辨率：0.20 m/cell
  PGM 尺寸：1800 x 750
  障碍高度切片：z=[0.03,0.80] m
  YAML origin：[-180,-75,0]
  自由像素：254
  障碍像素：0
  边界：最外一圈障碍栅格
  地图生成阶段安全膨胀：无

地图只表达场景原始 collision。Go2 机身尺寸和安全距离由 Nav2 costmap 的 footprint 与
inflation layer 处理，不写死在 PGM 中。

2.3 world 展开和 collision 读取

`world_to_grid` 使用无 shell 字符串拼接的子进程执行：

  gz sdf -p <world>

模型搜索路径合并 `--model-path`、`GAZEBO_MODEL_PATH` 和 `~/.gazebo/models`。转换器用 TinyXML2
遍历展开后的 `world/model/link/collision`，完全忽略 visual。

世界位姿递归组合：

  T_world_collision = T_parent_model * T_model * T_link * T_collision

无 `<pose>` 时使用单位变换；姿态解释为 `x y z roll pitch yaw`。支持普通父子 pose 和
`relative_to="__model__"`。无法解析的 frame 会硬失败，不能静默使用错误坐标。

所有 static 和非 static 模型都按 world 初始状态进入地图，dynamic 标志写入 CSV。机场 UAV
通过 `--ignore-model uav1_iris_depth_camera` 显式排除。

2.4 三维 AABB 首版几何规则

  box：变换局部包围盒 8 个角点；
  cylinder：用 [-r,r] x [-r,r] x [-length/2,length/2] 的保守包围盒；
  sphere：用半径包围盒；
  mesh：Assimp 加载 DAE/OBJ/STL，递归应用节点变换、DAE 单位和 up-axis、SDF scale、
        collision 世界位姿，再合并全部顶点。

高度与边界状态：

  max_z < 0.03              -> ignored_below_slice
  min_z > 0.80              -> ignored_above_slice
  XY 完全位于地图外         -> ignored_outside_bounds
  显式忽略模型               -> ignored_model
  与高度切片相交             -> occupied，投影完整 XY AABB

道路、跑道和地面 collision 的最高点约为 0.01 m，因此保持自由。建筑、车辆、飞机轮子和塔等
与 Go2 高度相交的物体会被保守覆盖。

plane、heightmap、submesh、未知 geometry、缺失 mesh、非法尺寸、非有限 AABB 或无法解析的
frame 都会硬失败，不允许漏掉障碍后继续生成。

2.5 栅格坐标和输出

世界坐标到栅格坐标：

  gx = floor((world_x - origin_x) / resolution)
  gy = floor((world_y - origin_y) / resolution)

PGM 行号：

  row = height - 1 - gy

只要 AABB 与某栅格存在正面积重叠就将该格标为障碍。YAML 使用：

  image: airport.pgm
  mode: trinary
  resolution: 0.2
  origin: [-180, -75, 0.0]
  negate: 0
  occupied_thresh: 0.65
  free_thresh: 0.25

转换器先完成全部临时产物，再替换正式文件；失败时不留下半成品。

CSV 字段：

  model,link,collision,geometry,static,status,
  min_x,min_y,min_z,max_x,max_y,max_z,source_uri

SVG 中黑色为有效障碍，绿色为低于切片的地面/道路，灰色为高空物体，并标注模型名。

三、旧版自研 A* 方案（历史保留，不再作为运行入口）
===================================================

旧实现文件：

  multi_go2_waypoint/multi_go2_waypoint/grid_astar.py
  multi_go2_waypoint/multi_go2_waypoint/waypoint_encircle.py
  multi_go2_waypoint/test/test_grid_astar.py
  multi_go2_waypoint/test/test_airport_astar.py

旧方案直接读取 PGM/YAML，在内存中按默认 0.55 m 半径膨胀障碍，使用八邻域 A*：

  直移代价：1
  斜移代价：sqrt(2)
  启发函数：octile distance
  open set：heapq
  禁止在两个障碍接触角点之间斜穿

A* 失败、起终点越界或位于障碍中时会明确报错，不会退化为穿障碍直线。路径通过 supercover
视线检查简化，再按最大 1.5 m 间距重采样为旧控制器航点。旧控制器到达每个航点后重新切换，
会出现用户观察到的密集航点停顿问题。

旧方案还会同步扩张围捕圆，直到三个目标点都位于膨胀后的自由区域。离线测试中默认 3.0 m
需要扩到约 4.0 m。

这个实现目前保留的目的：

1. 保存项目方法演化记录；
2. 提供基础 A* 教学和回归比较；
3. 在 Nav2 不可用时辅助检查地图连通性。

当前 airport 运行时不得同时启动旧 `waypoint_encircle` 与新 Nav2，否则两者会同时向
`/go2_i/cmd_vel` 写速度，造成控制冲突。

4.2 统一场景 YAML

每个场景 YAML 集中保存：

  world 文件路径
  地图包、地图 YAML 和 map frame
  目标 x、y、yaw
  围捕半径、扩张步长和最大扩张量
  planner_id
  go2_1/go2_2/go2_3 的出生 x、y、z、yaw
  RViz 轨迹颜色

机场配置是：

  config/scenes/airport.yaml

`Scripts/start_three_go2_velodyne.sh` 已改成用 `scene_config_dump` 读取 YAML，并把三只狗位姿
显式传给各自 spawn launch。city 不再暗中依赖三个 launch 文件内互不相同的默认值。

修改出生地点或朝向只改场景 YAML，然后重新启动仿真，不需要重新生成地图。修改围捕半径或
目标位置/朝向同样只改 YAML，并重新启动协调器。只有 world 内静态 collision、地图范围、
分辨率或高度切片改变时才需要重新生成 PGM/YAML。

city 和 forest 当前 `map: null`，可以继续用 YAML 启动 Gazebo，但不能启动纯 Nav2；先用
`world_to_grid` 给对应场景生成地图后再补齐 map 字段。

4.3 共享地图与 TF

系统只启动一个全局 `map_server`，发布 `/map`，避免三份相同地图占用资源。每只狗使用命名空间：

  /go2_1
  /go2_2
  /go2_3

Gazebo 的 ground-truth relay 发布：

  go2_i/odom -> go2_i/base_footprint

里程计数值本身就是 Gazebo world 坐标，因此 launch 为每只狗发布单位静态变换：

  map -> go2_i/odom

仿真中不启动 AMCL，避免 AMCL 与 ground truth 同时发布/解释定位。所有 Nav2 节点使用全局
`/tf` 和 `/tf_static`，没有采用官方多机器人 launch 中把 TF 重映射进命名空间的做法。

4.4 每只狗的 Nav2 组件

  controller_server
  smoother_server
  planner_server
  behavior_server
  bt_navigator
  velocity_smoother
  lifecycle_manager_navigation

全局规划器：

  nav2_smac_planner/SmacPlanner2D

它是 Nav2 提供的栅格 A* 系列规划器，不是本项目自研 A*。

局部路径控制器：

  nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController

RPP 持续跟踪整条 path，不再以“到一个人工航点、停一下、再前往下一个航点”的方式执行。
控制器输出先到命名空间内 `cmd_vel_nav`，再由 Nav2 `velocity_smoother` 以 20 Hz 平滑后发布到：

  /go2_i/cmd_vel

配置速度限制与当前 Go2 底层能力一致：最大前进约 0.65 m/s、最大角速度约 0.90 rad/s；RPP
期望线速度先保守设为 0.45 m/s。

4.5 Costmap 安全配置

三套 Nav2 都订阅全局 `/map`。全局 costmap 使用 0.20 m 分辨率；局部 rolling costmap 为
8 m x 8 m，0.10 m 分辨率。首版不依赖雷达，局部和全局均使用 static layer + inflation layer。

Go2 footprint：

  [[0.38,0.24], [0.38,-0.24], [-0.38,-0.24], [-0.38,0.24]]

膨胀半径：0.55 m；cost scaling factor：4.0。

这张 airport 地图没有动态障碍观测。后续如果要求处理突然出现的障碍，再把 Velodyne/2D scan
接入 obstacle 或 voxel layer；不应为此重做原始地图。

4.6 围捕协调器流程

`encircle_coordinator` 不含 A* 和速度控制，流程如下：

1. 读取同一份场景 YAML；
2. 等待三只狗 odom、`ComputePathToPose` 和 `NavigateToPose` action；
3. 以目标为中心生成等间隔的三个围捕 pose；
4. 每个 pose 的 yaw 始终朝向目标中心；目标 yaw 用于旋转整组候选点；
5. 请求每只狗到每个候选点的 Nav2 path，共 3 x 3=9 条；
6. 枚举 3!=6 种分配，用 Nav2 实际路径长度最小作为分配代价；
7. 如果没有完整可行分配，按 YAML 的 `radius_step` 同步扩大围捕圆；
8. 找到分配后，为三只狗并行发送 `NavigateToPose`；
9. 任一 action 被拒绝或失败时取消其余尚未结束的 goal；
10. 三个 action 全部成功才报告围捕到位。

协调器发布 `/go2_i/selected_plan` 作为分配时的稳定预览。Nav2 运行中的重规划路径发布在
`/go2_i/plan`。

机场的纯 Nav2 模拟里程计集成测试结果：3.00 m 候选没有完整可行分配，3.25 m 找到分配，
三条总规划长度约 252.12 m。实际 Gazebo 运行时路径会按真实起始姿态和 costmap 状态重新计算，
所以这个数字是集成检查结果，不是硬编码结果。

八、当前边界与后续方向
======================

当前版本解决：

  已知 world 的稳定离线地图
  三套真正隔离的 Nav2 规划和控制
  连续 path 跟踪与速度平滑
  围捕半径自动扩张
  基于 Nav2 实际路径代价的三狗目标分配
  同一 map 上三狗规划/真实轨迹可视化

  时空联合多机器人避碰
  真实定位漂移（仿真使用 ground truth）
  city/forest 的静态地图（配置已预留，map 仍为 null）

如果实际运行发生三狗路径交叉，下一步应在保持纯 Nav2 的前提下增加速度协调或分批放行，并把
其他机器人位置接入动态 costmap；不建议恢复旧版航点 P 控制器。


九、2026-07-21 现场问题与修复
=============================

首次真实三狗运行发现两个相互独立的启动/规划问题：

1. `ComputePathToPose` 和 `NavigateToPose` action server 已出现在 ROS 图中时，go2_3 的 Nav2
   lifecycle manager 仍可能尚未完成 active。协调器提前发出目标后，go2_3 拒绝目标，另外两只狗
   按全有或全无策略被取消。
2. 协调器曾同时向同一只狗的 planner 连发三个候选目标。Nav2 SimpleActionServer 会让这些请求
   互相抢占，planner 日志连续出现 `[compute_path_to_pose] Aborting handle`，导致 3x3 路径矩阵
   残缺并错误扩张围捕半径。

修复后的启动条件同时要求：三路 odom 已收到、三套规划/导航 action 已发现、三个
`/go2_i/lifecycle_manager_navigation/is_active` 均返回 success。

九条候选路径改为 goal-major 三批调度：

  批次 0：go2_1->goal0 || go2_2->goal0 || go2_3->goal0
  批次 1：go2_1->goal1 || go2_2->goal1 || go2_3->goal1
  批次 2：go2_1->goal2 || go2_2->goal2 || go2_3->goal2

每批内部三套独立 planner 并行；只有三条都返回后才进入下一批。因此同一 planner 同时最多一个
请求，但规划阶段仍利用三狗并行。九条路径收齐后进行 3! 分配，再同时发送三个
`NavigateToPose`，所以不会变成一次只控制一只狗行走。

最终分配增加两层硬校验：三个 goal index 必须唯一，三个 goal XY 坐标也必须唯一。日志逐条打印
`robot -> goal index -> coordinate -> status -> path length`，最终路径另打印 `FINAL` 行。

RViz topic 含义修正：

  /go2_i/plan           Nav2 最近一次内部规划，候选查询会反复覆盖，默认关闭
  /go2_i/selected_plan  三狗分配完成后锁存的最终分配路径，默认显示
  /go2_i/actual_path    ground-truth 实际行走轨迹，默认显示

此前三条 `/plan` 指向同一点，是因为三套 planner 最后都查询了相同编号的候选点，并不表示
`permutations(range(3))` 把三只狗分给了同一终点。修复后的 RViz 只把 `selected_plan` 作为最终
分配结果展示。

隔离 ROS domain 的三套真实 Nav2 集成验证中，九条路径均按三批成功返回，planner 阶段不再出现
`compute_path_to_pose Aborting handle`。半径 5.0 m 的最终分配为：

  go2_1 -> goal 1 (77.71,-29.44)
  go2_2 -> goal 0 (77.30,-20.79)
  go2_3 -> goal 2 (84.99,-24.76)

三套 `bt_navigator` 在同一时刻接受并开始执行三个不同的 `NavigateToPose`。测试使用固定 TF 模拟
静止机器人，因此约 15 秒后 controller 的 progress checker 按预期中止；该中止不属于候选规划
抢占问题，真实 Gazebo 机器人移动时应由实际里程计更新通过 progress checker。


十、三套 Nav2 同时 autostart 的 lifecycle 超时修复
=================================================

现场复测时协调器持续显示 `Waiting ... go2_1`。ROS 图中虽然已经能看到 go2_1 的 action server，
但 lifecycle 实际状态为：controller_server 是 inactive，planner_server、bt_navigator 和
velocity_smoother 仍是 unconfigured。go2_1 的 controller 日志给出了关键错误：

  failed to send response to /go2_1/controller_server/change_state (timeout):
  client will not receive response

原因是原 launch 同时启动 map 和三套 Nav2 lifecycle manager。三套 local/global costmap 同时接收并
配置 1800x750 静态地图时，首个 change_state 请求可能超过 Nav2 lifecycle service 的内部等待时间。
节点进程“已经加载”不等于 lifecycle 已 active；协调器等待 go2_1 是正确的全有或全无保护。

永久修复增加一次性 `nav2_bringup_sequencer`：

  1. map_server 和三套 Nav2 节点照常创建，但四个 lifecycle manager 的 autostart 固定为 false；
  2. sequencer 调用 `/lifecycle_manager_map/manage_nodes` 启动共享地图并确认 is_active；
  3. 依次调用 go2_1、go2_2、go2_3 的 manage_nodes，每一套确认 active 后才启动下一套；
  4. 协调器仍独立检查三路 odom、actions 和 lifecycle active，全部满足后才进行候选规划；
  5. 任一步拒绝、异常或 60 秒超时都会停止后续 bringup，协调器不会发送部分导航目标。

这里采用服务应答驱动的严格顺序，而不是写死若干秒延时，所以不同机器负载和地图大小下都能等待
上一套真正完成。默认 launch 命令保持不变。`autostart:=false` 时不会启动 sequencer，继续保留手工
逐套调用 lifecycle manager 的调试方式。这个启动顺序只影响 Nav2 节点激活；成功激活后三套 planner
仍按候选批次并行，三个 NavigateToPose 仍同时执行。


十一、Go2 路径跟踪摇摆与翻倒的保守控制修复
=============================================

现场规划路径正确，但实际轨迹末端反复打圈并最终翻倒。日志证明 FollowPath 发生
`Failed to make progress` 后，Nav2 默认恢复树反复执行 1.57 rad Spin 和 BackUp。更关键的是，
controller_server 通过 `cmd_vel_nav -> velocity_smoother -> cmd_vel` 输出，而 behavior_server 原先
直接发布 `cmd_vel`。恢复阶段 behavior_server 的非零旋转命令会与 velocity_smoother 的零速/旧命令
同时到达 CHAMP，造成速度指令交替、步态抖动和恢复动作持续失败。

另外，ground-truth odom 实测约 7-10 Hz，旧 controller 和 CLOSED_LOOP velocity_smoother 均为
20 Hz。四足侧滑速度被闭环平滑器当作控制反馈，在 Nav2 停止后仍可能产生小幅横向输出。

首轮保守修复如下：

  - behavior_server 的 cmd_vel 同样重映射到 cmd_vel_nav，最终 cmd_vel 只允许 velocity_smoother 发布；
  - 默认 BT 改为包内 navigate_to_pose_no_recovery.xml，仅做 1 Hz 重规划和 FollowPath；
  - 删除自动 Spin/BackUp 恢复循环，FollowPath 失败时安全终止，由协调器取消其余目标；
  - controller_frequency 从 20 Hz 降为 10 Hz；
  - RPP 期望线速度从 0.45 降为 0.22 m/s，原地转向从 0.60 降为 0.22 rad/s；
  - 最大角加速度从 1.50 降为 0.50 rad/s^2；
  - 到点容差改为 0.40 m，朝向容差改为 0.45 rad；
  - progress checker 改为 20 秒内移动 0.15 m，适配慢速步态；
  - velocity_smoother 改为 OPEN_LOOP，限速为 0.30 m/s 和 0.35 rad/s；
  - 平移/旋转最大加速度分别限制为 0.30 m/s^2 和 0.50 rad/s^2；
  - 指令超时从 1.0 秒缩短为 0.5 秒。

这里的 OPEN_LOOP 只指速度平滑器不再用瞬时侧滑速度修正下一条 cmd_vel；Nav2 controller 仍持续使用
ground-truth pose/odom 做路径闭环跟踪，因此没有退化为开环导航。后续应先单狗测试直行、低速转向、
单目标 FollowPath，再恢复三狗。稳定后每次只提高一个速度或加速度参数，避免无法定位回归原因。
